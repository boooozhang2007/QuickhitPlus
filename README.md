# QuickHit - 打字游戏

一个 Python 控制台打字竞速游戏，支持单机闯关、无限模式，以及联网的对战匹配、实时在线人数和全服排行榜。

## 游戏规则

- 控制台随机生成一串字母
- 玩家需要在限定时间内正确输入
- 闯关模式共 3 关，难度递增；无限模式关卡不断加长，直到失败

| 关卡 | 字符长度 | 时间限制 | 基础分 |
|------|----------|----------|--------|
| 第 1 关 | 4 | 10 秒 | 100 |
| 第 2 关 | 6 | 8 秒 | 200 |
| 第 3 关 | 8 | 6 秒 | 300 |

## 运行

**1. 先启动服务端**

```bash
python3 server/server.py
```

默认监听 `0.0.0.0:8888`。首次运行会自动在项目根目录创建 `users.json` 保存账号数据。

**2. 再启动客户端**

```bash
python3 client/app_start.py                  # 连本机 127.0.0.1:8888
python3 client/app_start.py <服务器IP> 8888   # 连远程服务器
```

也可以不带参数直接跑单机模式（不需要服务端）：

```bash
cd client && python3 app_start.py   # 需要先改回本地账号模式
```

## 通信协议

`shared/protocol.py` 定义了消息格式，服务端和客户端共用：

- 每条消息 = 4 字节大端长度头 + UTF-8 编码的 JSON 消息体
- TCP 是字节流，不保证一次 `recv` 正好拿到一条消息，所以必须自己定边界
- `recv_msg()` 内部循环读满指定字节数，对端正常关闭时返回 `None`

客户端发请求，服务端回同类型的 `xxx_result`；服务端还会主动推送 `online_count`、匹配成功的通知，以及对战结束的 `battle_over`。

## 对战流程

1. 两名玩家在客户端选「匹配对战」，服务端用 FIFO 队列两两配对
2. 配对成功后双方各自在本地打完一局**无限模式**，把分数上报给服务端
3. 双方都上报后，服务端按得分高低判定胜负（同分为平局），把结果推给双方
4. 对战成绩同样计入个人历史记录和全服排行榜；对手中途掉线会通知另一方结束对战

客户端上报分数用 `battle_result` 请求，服务端立即回 `battle_ack`（含 `waiting` 标志），
判定完成后再推送 `battle_over`。

## 服务端用到的数据结构

| 功能 | 数据结构 | 复杂度 |
|------|----------|--------|
| 账号存储、在线表 | 哈希表（链地址法 + 自动扩容） | 增删查平均 O(1) |
| 匹配队列 | 双端队列（FIFO） | 入队/出队 O(1) |
| 排行榜前 N 名 | 堆（自实现，大小为 N 的小顶堆） | O(m log n) |
| 个人历史成绩排序 | 快速排序（自实现，三数取中 + 小区间插入） | O(k log k) |
| 个人统计的排位 | 二分查找 | O(log k) |
| 分数段人数统计 | 值域线段树（自实现） | 查询 O(log V) |

哈希表在装填因子超过 0.75 时会自动扩容到约两倍大的质数，并把所有元素重新散列。
不扩容的话，固定 101 个桶装 5 万个 key，平均链长会到 495，查找就退化成顺序查找了。
扩容是 O(n) 的，但因为容量翻倍，摊还到每次插入仍然是 O(1)。

`server/sort.py` 里的排序和 Top-K 都是自己实现的，没有调用内置 `sorted()`。
`python server/sort.py` 会先与内置排序对拍，再对比插入 / 快速 / 堆排序在 1 万、5 万规模下、
随机 / 已升序 / 已降序 / 大量重复四种分布的耗时：快排在 5 万随机数据下约 120ms，
已降序（最费时的分布）约 172ms，堆排序则一直稳定在 250ms 上下；
排行榜用大小为 N 的堆选前 N 名，只需要 O(m log n) 而不是把全部玩家排序。
